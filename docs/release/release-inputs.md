# Release inputs and gates

Current build is a local development prototype. Production release requires owner-supplied Apple Team ID, registered bundle/helper IDs, Developer ID signing certificate, notarytool Keychain profile, support/privacy URLs, own production rule public key and endpoint. Commercial distribution additionally requires product IDs and approved entitlement/trial policy. No secrets belong in Git.

`DeveloperID` and `MAS` are wired into the Xcode project, Runner, RunnerTests, and Flutter Assemble. Both use Flutter release mode, universal arm64/x86_64 settings, macOS 12 deployment, hardened runtime, and channel-specific entitlements. Runner's ordinary `Release` configuration remains the local prototype. Check the wiring with `python3 docs/release/check-xcode-configurations.py` and inspect resolved settings with `xcodebuild -showBuildSettings -project App/macos/Runner.xcodeproj -target Runner -configuration DeveloperID CODE_SIGNING_ALLOWED=NO` (repeat for `MAS`). These checks neither build nor sign a distribution.

The channel configurations intentionally have no checked-in Team ID, registered bundle ID, or provisioning profile. Supply owner-controlled values only in the release environment after qualification; an empty resolved identifier is not a releasable app. `verify-artifact.sh` and the release report gate remain required. MAS is blocked by the current AX strategy even though its Xcode configuration is available for feasibility experiments.

For a qualified production build, pass `NECARAMBA_PRODUCTION_RULES_DIR` as an explicit Xcode build setting pointing to an owner-controlled directory outside the app bundle. It must contain exactly `manifest.json`, `signature.ed25519`, `payload.json`, `TrustedRuleKeys.json`, and `Licenses/` with at least one `.txt` attribution file. `TrustedRuleKeys.json` is a compact, sorted JSON map of production key IDs to base64 Ed25519 public keys, with no trailing newline. Also supply `NECARAMBA_TEAM_ID` and `NECARAMBA_BUNDLE_ID`; the resolved `PRODUCT_BUNDLE_IDENTIFIER` must match the latter. Do not put private keys in this directory or in Git.

The embed phase compiles and runs `ValidateProductionRulePackage.swift` against the same `NecarambaCore` verifier sources used at runtime. It checks bounded file reads, the signed manifest and payload, schema and app version, nonempty attribution, and rejects development markers, development/test key IDs, and the bundled development public key even if renamed. Only then does it copy the package to `Rules/Production` and remove any stale `Rules/Development`. Switching back to a local prototype similarly removes stale production resources. Run `python3 Tools/Release/test_validate_production_rule_package.py` for synthetic gate tests; its ephemeral signatures are test material, not owner release credentials.

`swift Tools/Release/validate-release-report.swift docs/release/release-report.json` intentionally fails until every required tuple has current artifact hash and a real evidence file with SHA256. The report must name the final artifact in `artifactPath`; `buildSHA` must be its measured SHA256. Each result must contain `status`, `evidencePath`, `evidenceSHA256`, `buildSHA`, `architecture`, `osMajor`, `osBuild`, `host`, and `adapter`. The JSON evidence file must independently record `status: passed`, the exact `tuple`, `artifactSHA256`, and matching architecture, OS major/build, host, and adapter. The CLI hashes both the artifact and each evidence file, and rejects any metadata mismatch. A passing fixture in `Tools/Release/test_validate_release_report.py` is synthetic gate validation only. Build/Swift/widget tests are not replacements for native Intel/macOS12, editors, real keyboard, TCC, sleep/wake or clipboard races. Commercial AC086–090 and MAS AC096 are excluded only from DeveloperID prototype manifest, not marked passed or declared generally unnecessary.

`Tools/Release/verify-artifact.sh Final.app` checks nested Mach-O architectures/deployment/signatures plus Developer ID, hardened runtime, notarization and Gatekeeper. It never signs or publishes. Sign nested components inside-out; after notarization staple and create a fresh final ZIP, then validate the extracted ZIP and a quarantined downloaded copy on a clean Mac.

Compatibility keys are `AC/architecture/OS-major/host/adapter`. The draft manifest names TextEdit, Safari, Chromium, Electron, and Necaramba across macOS 12, 13, and 27; each tuple requires its own measured evidence from a concrete host build. OS 27 replaces the old `current` placeholder and must be updated explicitly when support expands. Terminal/IDE automatic correction remains denied pending independent qualification.
